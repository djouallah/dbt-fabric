# The Sail SMOKE TEST, not an engine.
#
# DELIBERATELY NOT NAMED requirements/sail.txt. That stem is how pipeline.yml resolves an
# ENGINE's dependencies (`requirements/${ENGINE}.txt`), and how ci.yml's gating matrix names
# its jobs. Sail is a candidate sixth engine, not a sixth engine — giving it an engine-shaped
# requirements file is the first step toward something picking it up as one.
#
# Standalone environment, so none of the console-script collisions in CLAUDE.md apply: no
# duckrun (pins dbt-core<2), no dbt-oss, no adapter of any kind. .github/scripts/sail_smoke.py
# issues raw SQL over Spark Connect — dbt is not involved, because the question it answers
# (does MERGE INTO work through the OneLake Iceberg REST catalog) is about the ENGINE. If the
# answer is yes, dbt-sail goes in a follow-up.
#
# Unpinned on purpose. The point of the probe is to measure whatever LakeSail has shipped
# most recently; pinning would freeze the answer at the moment it was written, which is
# exactly the thing being tested. The log records the resolved versions.
pysail
# THE CLIENT ONLY, and never `pyspark` or `pyspark[connect]`. Those are the full Apache Spark
# distribution -- JVM jars and all -- which is the exact thing Sail exists to avoid: the whole
# claim being tested is that a Spark-compatible engine can run with no JVM anywhere. Pulling
# Spark in to talk to the thing replacing Spark would make the probe a lie about its own
# dependencies.
#
# pyspark-client is Apache's own slim Spark Connect client (grpc + pyarrow + pandas, no jars)
# and it keeps the `pyspark.sql` import path, so the script is unchanged. pysail's own test
# extra pins pyspark-client==4.2.0, which is the authority on what pairs with it.
pyspark-client
